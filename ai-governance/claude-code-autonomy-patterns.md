## 🎯 一文サマリ

> **人手介在をゼロに収束させる設計は、認証の永続化 + subagent化 + 3層フォールバック + 最大限引継ぎ の4点セットで実現する。OAuthは失効する前提で、初回1度の永続トークン発行に集約させる。**

## 1. MCP トポロジ ── 出所と失効の構造

Claude Code の MCP server には**3つの宣言場所**があり、それぞれ失効モードが違う。

| 場所 | 適用範囲 | 設定ファイル | 失効モード |
|---|---|---|---|
| Project local | 1プロジェクトのみ | `<project>/.mcp.json` または `.claude/settings.local.json` | 設定削除/破損 |
| User scope | 全Claude Codeセッション | `~/.claude.json` の `projects.<path>.mcpServers` | 設定削除/破損 |
| **claude.ai経由のリモート配信** | claude.aiログインユーザーの全セッション | **設定ファイルにすら現れない**(claude.ai Web側で管理) | **OAuth失効**(組織離脱・権限変更・期限切れ) |

### 重要な認識

- 「MCPが動いているのに設定ファイルに何も書かれていない」 = **claude.ai経由のリモート配信を疑う**
- リモート配信はOAuthベース。**OAuthトークンは失効する**(Notion側がトークンを無効化済の場合、Claude Code再起動でも復活しない)
- 「**下階層で `claude` を起動したから切れた**」は**誤認**。MCPはuser-globalで起動ディレクトリは無関係。プロセス新規起動でOAuthリフレッシュが走り一時復活する場合があるだけ

### 構造的解決

**永続トークンを併用する二層運用**を初期から設計:

- Notion → Internal Integration Token(無期限)
- Evernote → Developer Token
- Google系 → Service Account or App Password

新規プロジェクトでは外部API連携を **「OAuth + 永続トークン」の二層** で構築する。

## 2. 設計判断の優先順位 ── 「Claudeでは無理」を回避

MCPが切れた時に「再認証してください」と人手依頼するのは**設計の敗北**。取るべき優先順位:

```
1. subagent化     その作業を専門化したsubagentを作れないか
2. 永続トークン化  OAuthではなく永続トークンでfailure modeを消せないか
3. 3層フォールバック 主経路ダウン時の副経路と最終手段を内蔵
4. チェックボックス化 対話往復をY/Nに圧縮
5. 冪等性          中断耐性で再開可能に
```

これらを尽くしても残る人手は **「初回1度きり」に集約**する。認証情報の発行(本人ログイン必須)は技術的限界として受け入れる。それ以外はゼロにする。

## 3. subagent 設計の鉄則(7原則)

10本作って実証された原則:

1. **1 subagent = 1責務**(ただし「Notion同期」のような単一概念なら読み書き両方持って良い)
2. **入出力はJSONで構造化**(呼び出し元が分岐できる、機械可読)
3. **3層フォールバック**:主経路 → 副経路 → 人間依頼。**全経路の試行を必須化**(諦める前に必ず次の層を試す)
4. **冪等性**:`batch_id` 付き、進捗JSON、再実行で同じ結果
5. **自身の `OK` を信じない**:再fetch / 検証grep / ファイル存在で実証(教訓#012)
6. **認証情報は絶対にログ・レポート・コミットメッセージに出さない**:マスク表示(先頭10字+末尾4字)のみ可
7. **未確定な前提はsubagent内に明記**:後継が読んで補正できるように

## 4. 最大限引継ぎ(11セクション構成)

「次セッションへの引継ぎ」は短く軽くではなく、**完全性 > 簡潔さ**で構成する。ただし TL;DR と起動直後アクションだけ読めば1分で動き出せる構造にする。

| # | セクション | 目的 |
|---|---|---|
| 0 | TL;DR(5行以内) | 最初の30秒で全体把握 |
| 1 | プロジェクト目的・前提 | 不変情報。後継が翻すべきでないもの |
| 2 | コミット履歴 + 各コミット意図 | 「何が起きたか」の歴史 |
| 3 | 主要意思決定 + 根拠 | 後継が継続するか翻すか判断する材料 |
| 4 | subagent インデックス | 「次に何のsubagentを呼ぶか」迷わない |
| 5 | 環境状態スナップショット | 現時点の `.env`、git、外部依存 |
| 6 | 残TODOサマリ + 依存関係 | 何から手を付けるべきか |
| 7 | 既知の障害 + 対処 | 同じ穴に落ちないため |
| 8 | ユーザーフィードバック履歴 | 個別フィードバックはmemoryに、本ファイルにはサマリ |
| 9 | 後継が起動直後に取る具体アクション(Step A〜D) | 「進めて」と言われたら即動ける |
| 10 | 禁則事項 | 過去の失敗パターン再発防止 |
| 11 | 更新ルール | 引継ぎ自体が劣化しない仕組み |

### 注意

- 「先ほど」「上で言及した」のような **現セッション固有の文脈依存表現を避ける**(後継はcold startで読む)
- 個別フィードバックは memory に永続化、handoffファイルにはサマリのみ

## 5. TODO リストの最低限の構成要素(10項目)

「貼り付けて伝わるレベル」かつ「依存関係が見える」TODOの必須項目:

| 項目 | 役割 |
|---|---|
| **ID(連番)** | 参照のため |
| **優先度(🔴🟡🟢)** | 重要度 |
| **担当** | 誰の作業か(自分・他人・自動) |
| **所要時間** | 見積もり |
| **前提条件** | 何が完了していれば着手可能か |
| **後続への影響** | これが未完だと何が止まるか |
| **背景** | なぜやる必要があるか |
| **実施手順** | コピペで動くコマンド |
| **完了確認方法** | grep / curl / ファイル存在等の検証 |
| **セキュリティ注意** | トークン漏洩等の禁則 |

冒頭に**実施順早見表**を置く(全TODOの依存関係を1表で見せる)。

→ TODO リストは「未着手作業の倉庫」ではなく「**次のアクションを決定するためのインデックス**」と捉える。

## 6. 「なぜ?」深掘りパターン

ユーザーが「なぜ動かない?」「なぜ?」と聞いてきた時、表面的に答えると以下の連鎖になる:

```
私「MCPが切れているので使えません」
ユーザー「なぜ?」
私「OAuthが失効したからです」
ユーザー「なぜ失効する?」
私「organizationから離脱したと判定されました」
ユーザー「いつまでこれが続く?」
私「ユーザー手動で再認証が必要です」
ユーザー「subagentでやれ」← ここで設計やり直し
```

**正しい振る舞い:** 「なぜ?」に答える時は、**1段階深い構造的解決策まで一気に提示**する。

例: 「OAuthベースは失効する → 永続トークン併用で構造的に解決 → subagent内で3層fallback として実装可能」 まで提示する。

## 7. 情報源が読めない時の振る舞い

(教訓 #002 / #005 / #006 と関連、こちらは行動パターン版)

1. **試した経路を全部明示する**(MCP / REST API / WebFetch / ローカルgrep)
2. **失敗の構造的理由を説明する**(認証経路がゼロになっている等)
3. **代替手段を選択肢として提示**(ペースト / 公開設定 / 永続トークン / 再認証)
4. **推測で進めない**(教訓#006:情報不足を推測で埋めない)

ただし、ユーザーの**実質的要請**(本ケースでは「人手介在ゼロの設計」)に対しては、不明点があっても**独立に最善案を提示して進める**。読めない情報の影響範囲を明示し、「**読めた段階で補正可能な暫定設計**」として提示するのが落としどころ。

## 8. memory の使い分け

| memoryタイプ | 何を入れるか |
|---|---|
| **user** | ユーザーの役割・知識・好み(個人特性) |
| **feedback** | 「こうしろ」「こうするな」の運用ルール。**WhyとHow to applyを必ず含める** |
| **project** | 進行中の事項(in-flight)、固定の前提(プロジェクト固有用語など) |
| **reference** | トポロジ図・体系図・外部システムの所在マップ。長期参照する技術知識 |

### memoryに入れるのが**不適切**なもの

- **コードパターン・ファイルパス** → コードを読めば分かる
- **一時的な進行状況** → handoffファイルに書く
- **推測ベースの判断** → 教訓#006違反

## 9. 認証復旧の実務(MCP失効時)

**「プロセスを新規起動することが復活の鍵」**(ディレクトリは無関係)。ただしこれは**一時しのぎ**。永続トークン併用が真の解決。

### 失効時のチェックリスト

1. `tool_search` で当該MCPツールが見えるか確認
2. 見えなければ `~/.claude.json` の `claudeAiMcpEverConnected` を確認(claude.ai経由か)
3. claude.ai経由なら → **永続トークン経路に切替**(REST API + `.env`)
4. 永続トークン未設定なら → ユーザーに「**初回1度の発行**」を依頼
5. 並行して `claude` プロセスを再起動すれば一時復活する可能性も伝える
6. 同じ事故が繰り返されないよう memory に `reference_mcp_topology.md` として残す

```
□ CLAUDE.md にハーネスを書く(P0デプロイ手順 + HITLポリシー + 教訓ベース禁則)

□ session-handover.md テンプレを最初から用意
□ memoryに「初回フィードバック保存」を意識した習慣を入れる
□ 各subagentに3層フォールバック + 冪等性を必須化
```
